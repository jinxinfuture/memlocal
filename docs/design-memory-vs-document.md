# MemLocal 设计依据：记忆 ≠ 文档 ≠ skills

> 目标：让所有 code agent 都能轻松同步一份「公用记忆」。
> 本文回答一个前置问题——**我们做的这个东西，跟"一个写满记忆的文档"到底有什么区别？**
> 结论先行：**文档是记忆的「传输格式」（transport），不是记忆本身。文档能当 MVP 的接口，但当规模与自动化上来，纯文档会塌。**

---

## 1. 记忆 vs 文档：五个本质区别

文档（如一份 `CLAUDE.md` / `MEMORY.md`）是**扁平、静态、整体注入**的一段文本。Agent 每次把它整段塞进 context。
记忆是**结构化、可检索、会自动维护**的状态。区别在这五点，且文档全部做不到：

| 维度 | 纯文档 | 记忆系统（我们做的） |
|---|---|---|
| **(1) 检索 vs 整体注入** | 全部塞进 context，越长越糟（见 §3 论文） | 按相关性**只取相关几条**，context 有界 |
| **(2) 写路径 / 自维护** | 靠人手动改 | Agent 自动抽取事实并 `ADD/UPDATE/DELETE` 对账 |
| **(3) 冲突与时间** | 矛盾并排躺着，谁新谁旧分不清 | 有 `UPDATE` 语义 + 时间戳，新事实覆盖旧事实 |
| **(4) 来源与置信** | 纯文本，无法追问"这条谁贡献的、多确定" | 每条带 `source` / `confidence` / `updatedAt` |
| **(5) 作用域组合** | 一个扁平文件 | 可分层：全局用户记忆 + 项目记忆 + 会话记忆，按需拼装 |

**关键点**：当记忆只有几十条、且你乐意手动维护时，一个文档确实够用（我们的 MVP 就用文档当同步出口）。
但"让所有 code agent 同步公用记忆"意味着记忆会**持续累积、跨多 agent、还会变**——这时纯文档的三个致命短板暴露：
1. **context 通胀**：文档越大，塞进 context 越不可靠（中间死亡区，见 §3）；
2. **没人维护**：文档不会自己更新"我现在吃素了"去覆盖"爱牛排"；
3. **无法对账**：多个 agent 各自改同一份文档，冲突无法自动合并。

所以我们的架构是：**canonical store 用结构化 JSON 当唯一真相源，各 agent 的文档（CLAUDE.md 等）只是「导出投影」**。文档是接口，记忆是引擎。

---

## 2. skills vs memory（用户判断正确）

- **skills** = 可复用的**能力 / 指令**（"怎么用某工具""某种固定流程"），与具体人无关。经典参考是 Voyager（Minecraft）的技能库：把解决问题的方案沉淀成可调用技能。
- **memory** = **个人 / 情境状态**（"用户叫 Max、住杭州、讨厌标题党、在做 RAG 项目"），跟人绑定。
- 结论：**它是 memory，不是 skill。** 一个 skill 可以"消费"记忆（例如"写代码前先读 MemLocal"），但记忆本身不是技能。

## 3. 论文支撑（把设计立住）

1. **Lost in the Middle**（Liu et al., Stanford + Anthropic, 2023）& **RULER**（Hsieh et al., 2024）
   - 长上下文存在"中间死亡区"：信息在首尾召回好、在中间掉 30%+；多针检索时相互干扰更糟。
   - RULER 显示：标称 32K+ 的模型里只有约一半在 32K 仍保持可用性能；**有效上下文 ≈ 广告值的 25–30%**。
   - → 直接支撑 §1(1)：不能把记忆全写进一个文档整体注入，必须走"检索 + 有界 context"。

2. **Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory**（Chhikara et al., 2025, arXiv:2504.19413, ECAI 2025）
   - 在 LOCOMO 基准上比 OpenAI 全上下文高 **26%**（LLM-as-Judge），p95 延迟降 **91%**，token 成本省 **90%+**。
   - 核心：动态**抽取 → 合并 → 检索** salient 信息；图变体用带时间戳的实体-关系图做时间一致性。
   - → 支撑：结构化持久记忆 + 写路径对账是正确路线，且比"全上下文"便宜得多。

3. **Generative Agents**（Park et al., 2023, Stanford）
   - 记忆流（observation stream）+ 检索打分 = **Recency × Importance × Relevance** 加权 + 反思（reflection）压缩。
   - → 支撑：检索要带"重要性/近时"权重；**反思 = 智能遗忘**，好记忆是"知道丢什么"而非"存更多"。

4. **MemGPT / Sirius**（Packer et al., 2023, arXiv:2310.08560）
   - OS 式虚拟内存层级：主上下文(RAM) + 回溯存储(recall) + 归档存储(archival)；LLM 通过函数调用**自主**管理（append / replace / insert / search）。
   - → 支撑：分层内存（我们 L1 会话无损 / L2 压缩 / L3 持久）+ 写路径自维护，是已被验证的范式。

**一句话科学结论**：长上下文 ≠ 记忆。记忆 = 结构化存储 × 相关性检索 × 写路径对账 × 智能遗忘（反思/压缩）。纯文档只覆盖"存储"且是退化最严重的那种。

---

## 4. 本项目定位（基于以上）

- canonical store（结构化 JSON）= 真相源；各 agent 文档 = 导出格式（transport）。
- 适配器做双向转换：导入把各 agent 文档解析进 store；同步把 store 反生成回各 agent 文档。
- 目标形态：**开放本地格式 + CLI/适配器**，让任何 code agent 一行命令同步公用记忆（"记忆的 SQLite"）。

---

## 5. 下一步（把 MVP 做成"科学"的抓手）

1. **检索打分**：实现 Park 的 `recency × importance × relevance` 加权，导出时不再整段塞，而是按需取相关条目（先缓解 context 通胀）。
2. **反思/压缩（智能遗忘）**：周期性把零散事实压成高层摘要，解决"只存不丢"。
3. **LLM 对账**：`ADD/UPDATE/DELETE/NOOP` + 冲突解决（"现在吃素"覆盖"爱牛排"）+ 时间推理 + 置信度门控（解决上下文中毒）。
4. **评测**：用 LOCOMO 思路自建轻量 benchmark（单跳/多跳/时间/开放域），量化"记对了没、更新了没"，作为开发者引力井。
